# 诊断规则

## 实际案例

复述目标与边界，再拿最近一笔业务走查：起点、收到的资料、先处理的人、判断规则、交接、等待、异常恢复和最终交付。可接收脱敏消息与单据。分别记录 SOP 规定、实际动作及例外，标出差异；已有事实不重复问。无材料时不虚构采访或样本。

示例：“你想缩短客户询价到报价发出的时间。我先按这个边界拆。最近一单有没有因为规格不全来回补问？”

## 追问与停止

问题按四类缺口排序：价值（频次、投入、等待、返工）、判断（规则、例外、错误后果）、接入（来源、导出能力、口径）、成功（速度、质量、容量与实际费用）。每个问题记录 changes_decision，说明答案如何改变推荐。每轮最多 3 个，够支持试点就停；无答案时继续条件分析。

只有宏观目标时先列业务段与候选切口，不随意指定最大瓶颈。当不同答案会使结论相反时，先问清或保留条件，工程细节放待确认。

## 步骤分类

| type | 适用 | 必查 |
| --- | --- | --- |
| remove_merge | 无价值重复录入、确认或搬运 | 是否丢失必要控制，责任如何归属 |
| rules | 规则明确，输入稳定，结果可检查 | 规则版本与有效期、例外、重复执行 |
| ai_assist | 非结构化资料、检索、草拟 | 原文依据、质量核验、不确定时转人 |
| human_in_loop | 常规可处理，例外需专业判断 | 例外占比、审核成本、接手队列 |
| human | 谈判、承诺或不可可靠验证的判断 | 可否只自动准备资料 |
| foundation_defer | 数据权限缺失、口径冲突或收益不足 | 先补什么，何种证据会改变结论 |

允许类别为空。高频不自动等于值得建设，低频也可能因严重错误后果值得改造。

## 推荐与反证

比较保留现状、轻量调整与工程改造的边际收益、前提和维护负担，给简短决策依据，不输出无来源评分。检查：假设失效后是否仍有效；是否把工作转给其他人；审核补料纠错重试维护后是否还省时；表单和资料整理是否已足够；是否改善真正瓶颈。

将反证写成失败条件、验证方法和调整。决策可为 pilot、defer、needs_input；关键前提缺失不无条件推荐 pilot。不要承诺未验证的接口、组织配合或转化效果。

对业务方说“把图片规格整理成可检查字段，再检索带依据的历史资料”，工程交接再说明接口等细节。变更条件时保留节点编号，重算受影响指标和重新渲染，不重置整场对话。
